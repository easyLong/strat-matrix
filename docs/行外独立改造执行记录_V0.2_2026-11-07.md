## 1. 已落地内容

| 工作面 | 当前实现 |
| --- | --- |
| 实体与审计 | 14张业务表各有Entity，继承Serializable BaseAudit，包含六公共字段及逐列TableField/TableId映射；TableName对应真实现有DDL。表的ID写入方式保持原SQL语义，没有批量修改数据库主键 |
| SQL返回与参数 | 六个业务Mapper使用实体/投影行及写入Command，不再以Map声明业务行；结果视图分别使用明细、账号聚合、周期聚合、任务、分布等投影；查询条件为PlanningQueryCriteria |
| 快照边界 | SqlRows只在SQL与既有JSON快照之间转换；实体没有继承Map。标签树、冻结输入、配置文档以及行内原始字段适配仍保留动态文档，不为了字符串检查而改成空壳对象 |
| 事务 | 删除ManualDatabase。生产业务使用BusinessTransactions端口，经独立Spring代理调用@Transactional；普通人工提交、换题、配置两阶段发布、自动分段结果、流水确认保持原事务范围 |
| 隔离测试事务 | IsolatedBusinessTransactions只用于不启动Spring的隔离构造；行内资料读取仍使用其所属数据源的只读事务。这两类基础适配器有明确边界，不把远程调用塞进业务大事务 |
| 页面请求 | 分页、范围、换题、使用次数、目录查询、配置保存采用请求对象和校验；算法配置/标签文档由ConfigurationDocument接收，Java不改写Python的参数字典 |
| POST查询 | 增加16个显式POST映射，账号/选题目录、任务查询、配置/标签读取及保存等已有对应入口；仍保留显式旧GET/PUT兼容入口，未保留通配转发 |
| 通配转发清理 | LegacyPageController及PageRoutes已删除；未识别业务URL返回404，不透传Python。保留的dev.legacy配置类仅供行外已有本地HTTP适配器使用，不再注册页面代理 |
| 身份与权限 | 继续使用Actor、HostAccess、HostContextProvider；新增PlanningPermission能力元数据，可信能力标识放入请求属性，由宿主真正执行授权。标记本身不放行，也不代替SQL数据范围 |
| 动态运行配置 | PythonRuntimeSettings返回一次请求使用的完整URL/Token快照；AtomicPythonSettings支持整份原子替换；PythonClient及业务服务不需要重建。实际Apollo监听由宿主实现 |
| 报表写入 | PlanningSpreadsheetWriter集中封装Excel输出；默认公开POI实现保持现有字段、样式及公式保护。现场如使用EasyExcel，只替换一个Writer Bean，不重写查询或报表业务 |
| 调度 | 对外提供人工推进、自动策划、内容补齐、热点检查四个Handler，组合当前10种阶段；生产无私有定时器，行外只有一个LocalJobPulse模拟调用同样的Handler |
| 任务领取 | 人工任务增加持久化租约及owner校验，租约位于任务payload的execution_lease元数据，冻结input不变；执行前逐条领取，计算期间无业务事务，过期可恢复，旧owner不能回写 |
| 资料预检 | inside装配BankSourceFacts时执行启动检查；SQL读取器绑定实际SqlSessionFactory，解析全部10个SELECT，未替换占位或缺失语句时阻止启动。只解析，不打开数据库连接 |

实体/Mapper/Command位于entity及services；Controller、宿主装配、行外模拟仍按S1五模块边界放置。没有新增业务表、修改现有DDL或执行实际迁移。

## 2. 四个宿主Handler

| Handler | 阶段 | 宿主负责 |
| --- | --- | --- |
| ManualTaskAdvanceHandler | 配置待确认推进→人工任务领取/推进→Python算法唤醒 | 触发频率、批量、失败告警与下次执行 |
| AutoScheduleHandler | 配置待确认推进→自动任务推进及周触发检查→Python算法唤醒 | 脉冲频率；业务配置仍决定是否到周策划时间 |
| ContentCompletionHandler | 营销进度、营销过审分配/日期、自动营销引用、普通内容状态、可选内容流水写入 | 常规对账频率；每天3次显式传dispatchContentFlow=true |
| HotspotCheckHandler | 检查明天的热点空位→可用热点或冻结普通兜底 | 每天触发；按返回游标继续同日分页 |

请求对象为PlanningJobRequest：业务时间now、batchSize、按阶段区分的cursors，以及是否触发流水写入。结果为PlanningJobResult，包含阶段结果、nextCursors、needsNextTick和retry_required。

内容补齐中的独立阶段不会因为另一个内容能力暂不可用而全部停住：失败阶段保留旧游标并汇总为retry_required，其余独立阶段继续。配置失败则阻断依赖该配置的策划流程。受理算法请求始终不表示业务完成。

四个Handler不等于只能配置四条Cron。内容对账和每天三次内容流水可以调用同一个Handler并使用不同参数；调度平台仍拥有触发时间、重试、超时及告警。低层PlanningTaskService仍保留供精细调度和兼容现有代码使用。

示例见[宿主Handler薄壳](../java-backend/host-integration/PlanningHandlersHostJob.java.example)。

## 3. 新旧页面协议的切换

新Java健康结果增加`apiContract: "post-v1"`，前端默认auto模式据此选择POST查询及新保存入口。旧Java没有该标识时仍使用原GET/PUT路径，避免只更新前端构建产物就要求运行中的旧Java立即升级。

宿主可以在`setPlanningHttp`中显式设置`queryContract: 'post-v1'`。该选择发生在发送前；写入失败不会自动换另一条路径重试。切换宿主绑定时，旧健康请求的迟到响应也不能覆盖新绑定的协议。

新增映射列在[POST增量契约](../java-backend/contracts/api-contract.json)，原S0快照未覆盖。基线工具核对“原契约＋显式增量”，不能静默修改旧接口。

以下是有意保留的兼容项，**不能表述为已机械完成指南的全部规范切换**：

- 旧GET/PUT及存活/就绪探针仍保留；没有把所有历史接口删除后强迫消费者同日切换。
- 新请求对象采用小驼峰并接受旧名称别名；原页面返回字段、算法字典和枚举值没有批量改名。
- 201/202、401/403、409/422、429/503仍表达真实语义；没有把错误统一伪装成200。宿主响应壳继续通过PlanningResponseAdapter一次适配。
- JSON视图的分组、去重、全范围统计及分页继续使用显式count和LIMIT/OFFSET。没有为了引入PageHelper而改变既有统计口径。
- 默认Excel仍为POI；已抽出宿主Writer接口，没有在缺少宿主版本依据时宣称已切换EasyExcel或通过其内部BOM验收。

若客户要求完全退出旧字段和方法，应作为后续协议版本发布，同时迁移全部消费者；这部分尚未做成破坏式替换。

## 4. 整体验收入口

在仓库根目录、准备好Python开发依赖、JDK8/Maven缓存、Node16、Playwright和Chrome后运行：

```bash
python -m testing --browser --packaging
```

该命令依次执行V19固定回放、Python与工具测试、五模块清理及Java回归、前端单测/构建、隔离Java/H2三页面浏览器、dev/inside构建及产物检查。Python测试加载禁止真实MySQL和公网模型调用的测试插件。

只清理五个新模块的target，保留根旧target，避免误删仍在运行的旧启动包。产物检查会拒绝残留的LegacyPageController/PageRoutes class，防止仅删除源码但旧class被再次打入JAR。

生产/真实模型验收不属于该命令：`testing.live --execute`和`testing.content_live --execute`仍为独立显式入口。本轮没有调用这些入口，也没有发布V9或重启现有服务。

验收结果及限制见[整体测试记录](整体回归结果_2026-11-07.md)。源码、接入模板及验收文档统一提交至`feature/planning-v2`分支；数据库发布和运行服务切换仍需单独执行。
