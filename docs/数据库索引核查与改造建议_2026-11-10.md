# 数据库索引核查与改造建议

核查日期：2026-11-10。源码基线：`00c94fe4dd21a62b95e62a541e5dd1954cbf5ea2`。

## 范围与结论

对照 Java 的 14 张业务表、Python 的 25 张算法表，以及实际 Mapper、任务领取和查询代码进行静态核查。未连接行内数据库，未取得行内 SHOW INDEX、统计信息、慢 SQL 或 EXPLAIN；下列属于候选方案，不代表已上线索引或实测性能结论。本次不执行 DDL，也不修改应用代码。

最需要处理的是：

1. 高频查询涉及的部分字段存储在 LONGTEXT 格式的 JSON 快照中，当前 SQL 每次提取后再筛选。仅把视图改成子查询，不能解决这些字段的索引访问问题。
2. 调整记录查询、账号占用释放、人工任务领取等存在明确的索引缺口或组合顺序不足。
3. V5 升级脚本定义了两个周次索引，但当前基础建表和 V9 新库完整安装脚本没有带上，存在安装路径差异。实际数据库是否缺失仍须 SHOW INDEX 核对。
4. 多个搜索使用 LOCATE(LOWER(...)) 包含匹配，普通 B-tree 索引通常不能据此进行有效范围定位。字段落列和建立单列索引之后，也不能直接宣称该搜索已得到优化。

建议将“取消视图”和“高频查询字段落列、索引及 SQL 调整”作为一轮关联改造，逐项验证，不给所有筛选字段机械地各加一个索引。

## 需要先从快照落到普通列的查询字段

这部分比“多加几个索引”更重要。索引只建在最终实际查询的列／表达式上，不能对 JSON 内的展示别名直接执行 CREATE INDEX。

| 表 | 当前主要藏在 payload 内的字段 | 建议处理 |
| --- | --- | --- |
| `godp_planning_batch` | batch_code、task_name、plan_type、cycle_start、cycle_end、内容状态及统计字段 | 先提取频繁定位／筛选的编号、方式、周期及内容状态。按实际页面查询建立如 `(plan_type,week_start)`、`(content_status,week_start)` 的候选，不把全部可选条件堆成一个巨型索引。统计字段只有筛选／排序需求时才考虑索引。 |

| `godp_manual_task` | task_name、publish_date；内容状态来自关联批次快照 | 任务投放日期落列后才可评估 `(publish_date,del_flag)`。created_by 已有正式审计列，优先复用并核对历史值，不新增同义的创建人字段。策划状态 status 与内容状态应分别处理。 |
| `godp_planning_task_archive` | task_code、task_name、publish_date、历史创建人及内容状态 | 若历史列表仍需在线筛选，补齐查询列并回填；归档量小时优先按时间范围限制。普通任务、营销任务与归档 UNION 后需保持字段类型、NULL 语义和全局排序一致。 |

新增查询列时，原 payload 继续承担冻结快照和完整详情职责。生产写入、换题、热点补题、营销引用、内容状态刷新、历史导入必须在同一事务更新相关查询列；否则索引很快但结果错误。为历史数据回填并做列值／快照一致性检查后，查询再切换到新列。

账号 ID、属主 UM、批次号应区分精确查询与名称包含搜索。当前 LOCATE/LOWER 查询不能通过给原字段建立 B-tree 索引就自动变成高效查询；不能未经业务确认把“包含”改成“前缀”。如须保留大范围包含搜索，评估宿主已有搜索能力或限制查询范围，不在本轮自行新增中间件。

## 实施与验收

1. 在行内取得各表 SHOW CREATE TABLE、SHOW INDEX、行数级别、常用筛选组合、是否强制机构范围，以及 MySQL 实际版本；以行内现状为准去重。
2. 取消视图与字段落列同步设计。明确 batch/item/task 三类查询的 SQL、分页、排序及实体列来源，保留 del_flag 和 write_state='ready' 发布边界。
3. 第一批优先验证：调整记录、占用释放、人工任务领取、周索引发布缺失、按投放日扫描、活跃算法流水线扫描。
4. 对精确账号、属主 UM、批次、时间范围及高频组合逐条 EXPLAIN。记录使用的 key、访问类型、估算行数、临时表／排序，再用代表性数据实测耗时、实际扫描量和并发写入表现。
5. 单列、复合索引遵循实际谓词前缀。状态低基数仍可能适用于稀少待处理任务；不能一律否定，也不能只建 del_flag/status 就认为所有查询都被覆盖。
6. 发布建表、存量 ALTER、回退、核查及契约校验值；同时记录哪些旧索引被替换，不能只不断叠加索引。DDL 交 DBA 按现场流程执行。
7. 不将所有 PRIMARY KEY 访问强制改成复合索引；不把覆盖扫描误判为选择性定位；不以 EXPLAIN 出现某个 key 就宣布达标。UNION、IN、OR、GROUP BY、深 OFFSET、contains 搜索及全量导出单独验证。

## 技术依据

- MySQL 组合索引按左前导列支持访问，单独出现某个后置列不等于有同等定位能力：[Multiple-Column Indexes](https://dev.mysql.com/doc/refman/8.0/en/multiple-column-indexes.html)。
- B-tree 范围访问受谓词形状影响，含前导通配符的 LIKE 不属于普通前缀范围定位；当前 LOCATE/LOWER 也不应据普通列索引承诺高效定位：[Range Optimization](https://dev.mysql.com/doc/refman/8.0/en/range-optimization.html)。
- InnoDB 二级索引携带主键列，新增尾部 id 要判断是否冗余：[Clustered and Secondary Indexes](https://dev.mysql.com/doc/refman/8.0/en/innodb-index-types.html)。
- JSON 路径值应通过明确的可索引表示处理，普通快照列上的索引不能直接当作各路径索引；是否允许生成列／表达式索引须按目标版本及行内规范判断，本方案优先普通实体列：[JSON Data Type](https://dev.mysql.com/doc/refman/8.0/en/json.html)。
