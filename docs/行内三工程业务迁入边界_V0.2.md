# 行内三工程业务迁入边界 V0.2

日期：2026-11-02。以当前仓库代码为准。目标工程是行内现有的 Vue、Java、Python 三个项目；本仓库的独立启动壳不作为行内部署单元。

## 一句话边界

Vue 只调用 Java；Java 持有登录权限、业务配置、任务状态、正式策划批次与槽位、结果查询和导出；Python 持有标签、画像、向量、匹配策略与计算。账号、选题、过审营销内容及内容生产状态是行内已有事实，由 Java 查询能力提供给页面或 Python。两个数据库按职责隔离。

## Java 驻场最集中的替换点

### 资料查询按四个能力分别替换

原来的 `ManualPorts.Source` 同时包含账号、选题、冻结输入和旧历史资格。现在它是业务服务消费的稳定门面；驻场实现分别落在四个小接口，再用 `HostSourceAdapter` 组合。业务服务和页面 Controller 不需要知道行内 SQL、SDK 或表名。

| 宿主实现 | 需要接入的行内能力 | 代码入口 | 是否允许用本地实现 |
| --- | --- | --- | --- |
| `AccountFacts` | 账号列表、按 ID 补全账号资料 | `accountOptions`、`sourceAccounts` | 否 |
| `TopicFacts` | 可选选题列表、选题详情 | `topicCandidates`、`topicDetail` | 否 |
| `SnapshotFacts` | 一次性读取选中的账号／选题并冻结算法版本；返回 `accounts`、`topics`、`algorithm_version` | `snapshot` | 否 |
| `HistoricalEligibility` | 迁移前的已策划和处理中占用资格；新任务占用由 Java 业务库判断 | `historicalPlanned`、`historicalReserved` | 仅确认没有旧历史时可显式返回空集合 |

宿主配置只装配一次门面：

```java
@Bean
ManualPorts.Source planningSource(ManualPorts.AccountFacts accounts,
    ManualPorts.TopicFacts topics, ManualPorts.SnapshotFacts snapshots,
    ManualPorts.HistoricalEligibility history) {
  return new HostSourceAdapter(accounts, topics, snapshots, history);
}
```

四个能力可由行内不同团队分别实现。`historicalReserved` 必须独立实现，不能默认等于 `historicalPlanned`，因为处理中账号也要占用资格。旧历史完成迁移后，这个接口仍显式返回空集合，删除旧过渡查询时再整体退出。`snapshot` 必须以实际选中 ID 为准，遇到已失效账号或选题时不要补造数据；业务服务会校验缺项。

### 其余接入按职责分开

| 模块 | 宿主接入点 | 保持不动的策划代码 |
| --- | --- | --- |
| 登录人与权限 | `ManualPorts.Actor`、宿主统一鉴权／审计 | 人工与配置业务服务 |
| Python 算法 | `ManualPorts.Computer`、`AutoSchedulePort` 的行内 HTTP 实现 | 人工任务与自动任务状态机 |
| 内容系统 | `ContentStatusSource`、`MarketingStatusSource` | 内容状态投影和业务进度计算 |
| 业务库 | `ManualDatabase`、`BusinessConfigDatabase`、`AutoScheduleMapper` 使用同一个业务库 MyBatis 工厂和事务管理器 | Repository、Mapper XML 和业务规则 |
| 行内调度 | 宿主 Job 调用人工任务推进、内容状态对账和自动周策划触发 | 持久化任务执行逻辑；`standalone/LocalJobPulse` 不迁入 |
| Vue 宿主 | 统一 API 前缀、路由、会话及下载响应适配 | 三个页面的业务交互与字段契约 |
| Python 资料入口 | `bank_bridge/factory.py` 选择 `java_http`，`java_http.py` 配置行内接口路由与响应映射 | 打标、向量、V2 匹配与算法策略 |

推荐迁入顺序：业务库表／Mapper → 身份与四类资料能力 → 人工计算 HTTP → 内容状态 → 宿主 Job → 配置综合保存 → 自动正式结果验收。每一步先验证对应业务闭环，再开启下一个模块。`planning.auto-schedule.enabled` 在目标双库迁移与正式提交验收前保持关闭。

1. `ManualDatabase`、`BusinessConfigDatabase` 与 `AutoScheduleMapper` 绑定宿主业务库的 MyBatis `SqlSessionFactory` 和同库事务管理器；Mapper XML 必须被加载。SQL 由行内发布，不复制本地建表类。
2. `ManualPorts.Actor` 从可信会话取 UM；数据权限、菜单权限和操作审计由行内接入层提供，不接受浏览器伪造的身份请求头。
3. `ManualPorts.Source` 由行内账号、选题、营销内容查询实现；`ManualPorts.Computer`、`AutoSchedulePort` 由行内认可的 Java→Python 客户端实现。
4. `ManualPorts.ContentStatusSource` 与 `MarketingStatusSource` 从行内内容系统读取真实状态；`ManualPorts.Transition` 只用于旧历史过渡，不能成为长期依赖。
5. 宿主调度器推进人工任务、内容状态和自动任务；不复制本地 `@Scheduled`。页面统一从 Java 入口查询状态。

以上替换集中在宿主接入配置、Mapper 绑定、资料／内容查询和内网 HTTP 适配。已实现的人工策划规则、幂等判断、换题限制和页面字段不应为适配宿主而重写。

## 发布前的实际缺口

上次只读预检中，本地配置指向的 `strat_matrix_bus` 尚无 `godp_manual_marketing_task`、`godp_auto_planning_task`，旧 `godp_planning_item` 尚无 `slot_id`。新库使用完整业务 DDL；旧库按表结构发布 V3、自动任务建表或 V4，再部署新包。算法库还需新增 Pipeline 提交归属和不可变提案表。Java 调度仍默认关闭，运行服务尚未切换；新代码的普通自动链路可由 Java 正式落库，热点／营销及综合配置仍待迁移。**代码已具备接口边界，不等于三个页面的业务均已完成行内迁入。**

最需要行内提供的实际信息：业务库 Mapper／事务 Bean；账号、选题和内容状态的查询对象及字段；可信身份与权限接入；Java→Python 内网鉴权、超时与宿主调度调用方式；旧历史结果保留或迁移方案。
