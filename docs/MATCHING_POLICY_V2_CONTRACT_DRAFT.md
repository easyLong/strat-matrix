# V2 匹配策略契约草案：标签适配、硬过滤、缺失数据与槽位复用

状态：**账号特征映射与多特征 Fit 仍是待评审草案**。组合目标 V2 已另行接入生产执行器，但当前执行器明确沿用 cosine Fit；本文的账号侧 T1–T6 映射、特征权重和缺失策略尚未进入该执行器。

## 1. 当前数据事实

选题侧已经有：T1 业务属性、T2 经营作用、T3 主题域、T4 目标客群、T5 生活场景、T6 用户需求；T3、T4、T5 是“分类组 → 叶子标签”两层结构，T1/T2 为固定单层枚举，T6 为语义归并的需求短语。T1–T5 有版本化稳定 ID；T6 有独立稳定 ID 与向量。

账号侧当前画像包括人设、账号标签、目标客群、兴趣、家庭身份、表达风格、属地和近三个月互动内容等。账号目前**没有**与选题 T3/T4/T5 同版本的稳定分类标签。因此不能直接将“选题 T4 ID”与“账号 T4 ID”比较，也不能把标签名称相同当作稳定关联。

V2 输入应冻结 taxonomy version、标签稳定 ID、分类父级路径、账号画像来源时间、互动窗口、模型标识、向量维度和语义空间 ID。缺少这些身份信息时不得跨版本拼接。

## 2. T1–T6 与账号画像的映射

| 选题维度 | 业务含义 | 账号侧证据 | V2 用法 |
| --- | --- | --- | --- |
| T1 业务属性 | 选题自身的业务属性，如营销/非营销 | 账号营销资质只表示账号资格，不是选题属性 | 不进入 Fit；不改变选题来源池。普通/营销/热点资格以槽位类型和来源接口为准。只有经业务确认的槽位兼容表可将 T1 用作硬过滤 |
| T2 经营作用 | 流量/转化目标 | 冻结的生命周期阶段、经营目标、该账号本周期已分配角色 | 先由配置形成槽位目标角色；若槽位目标已固定，则 T2 必须与槽位角色相符。T2 不作为账号兴趣 Fit |
| T3 主题域 | 选题所属主题 | `account.interests`、`account.account_tags`、人设文本、近窗内容标题 | 账号侧证据经版本化映射到 T3 分类/叶子，计算主题适配；没有映射时可用主题语义信号，但须标记低证据覆盖 |
| T4 目标客群 | 选题主要面向的人群 | `account.target_audience`、`account.family_identity`、人设文本 | 目标客群字段为优先证据；父级分类用于较宽的人群匹配，叶子标签用于精确匹配 |
| T5 生活场景 | 选题发生/使用的场景 | 近窗真实内容标题、兴趣、地域；必要时账号运营场景描述 | 以场景证据匹配。账号城市只参加属地硬过滤，不自动当作生活场景兴趣 |
| T6 用户需求 | 用户希望解决的具体问题 | 近窗内容标题/互动、兴趣、人设及其生成的需求语义向量 | 使用同一向量模型空间计算需求相关性；T6 的 0.80 归并阈值只用于 T6 标签去重，**不得**作为匹配阈值 |

### 2.1 层级标签适配

选题侧先按 `taxonomy_version + tag_id` 还原 T3/T4/T5 的完整路径。匹配分值按以下层级关系计算：

- 账号证据命中相同叶子：精确命中；
- 账号证据只命中相同父分类：父级命中，低于叶子命中；
- 命中不同分类：结构化标签不命中；仍可由单独的语义特征判断相关性；
- 账号证据没有可映射标签：记为缺失，不能当作不相关的 0 分。

叶子/父级分差应作为 V2 策略参数保存。初版草案建议叶子命中 1.0、父级命中 0.6；这两个值需要用运营标注样本校准。

### 2.2 账号侧特征生成

准备快照应新增可审计的 `account_matching_features`，至少包含每项证据的来源和更新时间：

```json
{
  "taxonomy_version": 3,
  "T3": [{"tag_id": "...", "path": ["本地生活", "城市服务"], "evidence": "interests"}],
  "T4": [{"tag_id": "...", "path": ["职业身份", "职场白领"], "evidence": "target_audience"}],
  "T5": [{"tag_id": "...", "path": ["出行场景", "日常通勤"], "evidence": "recent_content"}],
  "T6": [{"text": "日常资金管理", "embedding_model": "...", "vector": [0.1, 0.2]}],
  "evidence_as_of": "2026-10-21T00:00:00+08:00"
}
```

账号标签映射只允许从明确来源字段生成，不让模型凭账号昵称猜客群。模型推断结果必须带 `evidence`、置信度和特征版本；低置信或无证据的标签按缺失处理。特征构建可以使用当前共用向量模型，但不得在匹配每条候选边时临时调用模型。

## 3. Fit 组成与缺失值口径

### 3.1 Fit 特征

第一版建议 Fit 只包含可解释的适配信号：

| Fit 信号 | 初始权重草案 | 说明 |
| --- | ---: | --- |
| `theme_T3` | 0.20 | 主题域标签层级适配 |
| `audience_T4` | 0.20 | 目标客群适配 |
| `scene_T5` | 0.15 | 生活场景适配 |
| `need_T6` | 0.25 | 用户需求语义适配 |
| `persona_fit` | 0.10 | 选题与账号人设适配 |
| `expression_style_fit` | 0.05 | 账号表达风格与选题表达要求适配；选题侧无表达要求时此信号缺失 |
| `profile_semantic_fit` | 0.05 | 完整账号与选题画像的语义适配；仅在独立语义空间校验通过时使用 |

权重合计为 1.00。该组数值只是可用于首轮影子评估的起点，不是批准值。`profile_semantic_fit` 与 T3–T6 有信息重叠，评估时必须单独对照“包含/不包含”版本，避免语义重复加权。

城市、账号状态、资格、槽位角色、生命周期及热点有效期属于门槛或组合约束，不计入 Fit。粉丝数与互动量默认用于生命周期判定，不直接奖励大账号，避免高粉账号天然压过内容适配。

### 3.2 缺失规则

1. **硬约束字段缺失**：不把空值当通配。若影响某账号/选题组合，则拒绝该候选边并记录原因；若缺失使整批资格无法判断，则阻断本次任务，要求补齐输入。
2. **标签未命中与标签缺失分开**：明确映射到不同叶子是 0 分；没有账号标签证据是缺失，不能按 0 分处理。
3. **Fit 缺失处理**：不做零值填充。允许按可用特征权重重新归一化，但可用权重覆盖率必须达到策略中的 `minimum_weight_coverage`；否则拒绝该候选边，原因 `fit_coverage_below_minimum`。
4. **初始覆盖率草案**：`minimum_weight_coverage = 0.70`。该值需通过影子评估确认。选题没有完整 T1–T6、T3–T5 taxonomy 版本不一致、T6 向量空间不一致，不属于可忽略的 Fit 缺失，应在准备阶段阻断。
5. **语义空间缺失/不一致**：禁止比较向量；若该策略要求语义信号，则任务阻断，不悄悄退化到标签分数。
6. **历史覆盖不完整**：不能把“未知历史”解释成“没用过”。若配置要求历史去重而快照不完整，任务阻断；完整性策略必须写入冻结策略。

Fit 输出 0–1，并保留 `raw_signal`、`weight`、`weighted_contribution`、`missing_reason`、`coverage`。给旧结果模型写入时由独立适配层按版本转换，不能混用分值尺度。

## 4. Hard Gate 初版规则

按以下顺序判定每个账号-槽位-选题组合；任何硬门槛失败即不参与 Recall/Fit，并保留全部拒绝原因：

| 规则 | 条件 | 缺失/失败处理 | 建议原因码 |
| --- | --- | --- | --- |
| G1 账号快照 | 账号在本批冻结快照内且状态有效 | 账号状态未知时阻断批次；明确无效时排除账号 | `account_status_unknown` / `account_inactive` |
| G2 槽位来源 | 普通槽只接普通选题来源；营销/热点由各自来源和资格规则处理 | 来源类型缺失或来源池不符时排除 | `topic_source_unknown` / `topic_source_mismatch` |
| G3 选题可用 | 选题状态可用，且评估时点落在有效期内 | 状态/有效期无法判定时排除，不以空值延长有效期 | `topic_unavailable` / `topic_validity_unknown` |
| G4 标签与画像 | 选题标签已完成，T1–T5 稳定 ID 与版本有效，T6 稳定 ID 有效，画像与向量版本一致 | 失败选题不进入候选池；若整个池无有效选题则阻断任务 | `topic_tags_incomplete` / `topic_profile_stale` |
| G5 向量空间 | 必须匹配相同的实际模型标识、维度和 `semantic_space_id` | 任一不一致时阻断任务，禁止混算 | `semantic_space_mismatch` |
| G6 属地范围 | 选题 `applicable_cities` 为空表示不限城市；非空时账号 `city` 必须精确命中 | 账号城市缺失且选题有限定城市时排除；不做模糊城市匹配 | `city_unknown` / `city_not_applicable` |
| G7 T2 槽位角色 | 槽位角色由冻结生命周期目标和周期组合规则产生；若该槽位角色固定，选题 T2 必须相同 | 角色或 T2 缺失时不把它默认为“流量”；排除候选并审计 | `slot_role_unknown` / `topic_role_mismatch` |
| G8 T1 属性 | T1 不改变选题来源池，不自动把普通来源转为营销来源 | 只有策略明确配置 `allowed_T1_by_slot_type` 时才按表过滤；无配置时不作为 Gate | `topic_business_attribute_mismatch` |
| G9 账号历史 | 同账号在冻结去重窗口内已用过的选题不可再次匹配 | 历史不完整且要求去重时阻断批次 | `account_topic_seen_in_history` / `history_incomplete` |

T1 的这一处理遵循既有业务口径：T1 是选题属性，不替代 IF 来源类型。营销资格是账号与槽位资格，不可从 T1 标签推断。

## 5. 槽位复用规则

### 5.1 初版建议

- **同账号、同一策划周期**：同一选题最多分配 1 次。这是硬约束，避免同一账号一周重复选题。
- **同账号、跨周期**：排除冻结历史窗口内已使用选题；窗口天数是必须配置的策略参数。窗口外的复用可参与，但应在 Fit/组合效用中保留重复事实。
- **跨账号、同周期**：不默认全局一题一账号。按运营池规模可设每题全局容量；未配置时视为不设硬上限，由 MMR/组合效用降低重复，不伪造固定容量。
- **同一账号不同槽位**：普通、营销、热点按独立槽位类型执行各自 Gate；组合层再统一检查选题重复和经营作用目标。热点待定题不占用普通选题，也不记为已使用选题。
- **正式使用次数**：未知必须保留为未知；不按 0 次参加排序。使用次数是软排序/组合信号，不替代同账号历史硬去重。
- **人工策划**：不进入 AI 匹配 Fit；若产品规则要求同投放日期账号不能再次人工策划，使用人工策划的独立日期约束，不混入 AI 选题复用规则。

### 5.2 配置字段

```json
{
  "reuse": {
    "same_account_same_cycle_max": 1,
    "same_account_history_window_days": 90,
    "history_unknown_policy": "block_task",
    "global_topic_capacity_mode": "unbounded",
    "global_topic_capacity_by_id": {},
    "usage_count_unknown_policy": "keep_unknown"
  }
}
```

示例中的 90 天只是初始评审建议；应与历史数据接口可提供的完整窗口核对后确认。`global_topic_capacity_mode` 只能在 `unbounded` 或 `configured` 中选择；选 `configured` 时必须为每个可参与选题提供正整数容量，不允许部分遗漏。

## 6. 一份可审计的 Fit 记录

```json
{
  "account_id": "ACC-001",
  "slot_id": "ACC-001:2026-11-02:01",
  "topic_id": "TOPIC-101",
  "fit_version": "v2-draft-1",
  "taxonomy_version": 3,
  "signals": {
    "theme_T3": {"score": 0.8, "evidence": ["interest:T3-LEAF-4"], "weight": 0.2},
    "audience_T4": {"score": 1.0, "evidence": ["target_audience:T4-LEAF-2"], "weight": 0.2},
    "scene_T5": {"score": null, "missing_reason": "no_account_scene_evidence", "weight": 0.15}
  },
  "fit_weight_coverage": 0.85,
  "fit_score": 0.82
}
```

审计记录存内部任务结果，不扩展运营页面。对外结果仍提供账号、槽位、选题及业务状态。

## 7. 当前代码落点与接入边界

- `matching_algorithm_v2.py` 已支持严格权重校验、禁止零填充、显式最低权重覆盖率、候选边拒绝记录、MMR 增量效用和容量约束矩阵分配。
- Hard Gate、账号侧 T3–T5 特征映射和 T6 账号需求向量仍需实现为版本化组件；本文给出其接口契约和数据来源。
- V2 必须使用新的 `implementation_key`、审批校验与审计结果 schema；不能改写 V1 的 `ALG-01–09` 语义、五阶段 `MatchingEvaluation` 或历史策略。
- 本草案尚未批准；0.6 层级分、权重、0.70 覆盖率和 90 天历史窗口都必须经过运营样本评审后，才能写入批准策略。
- 覆盖、平衡、冗余的公式以及 MMR 在候选搜索中的定位见[组合目标草案](MATCHING_PORTFOLIO_V2_DRAFT.md)。
