# 策划结果三工程改造 V0.1

2026-11-03 进展：普通自动策划新增 Java 提案校验、幂等批次／槽位事务和 Python 确认重试，并复用 Java 结果查询。数据库及运行服务未切换；热点补题、营销内容引用和旧历史迁移仍待处理。新增契约与发布步骤见[正式提交与确认](自动策划Java正式提交与确认_V0.1.md)。下文保留首轮结果结构改造记录。

日期：2026-11-02。目标是让策划结果成为 Java 业务事实，Python 只返回算法提案；Vue 只调用 Java，保持现有账号列表、时间列表、三个策划详情和导出入口。

## 工程边界

| 工程 | 策划结果职责 |
| --- | --- |
| Vue | 筛选、分页、列表、详情、导出与换题交互；请求统一进入 Java |
| Java | 确认结果、保存批次和槽位、查询汇总与详情、操作记录、内容状态投影、数据权限和导出 |
| Python | 账号选题匹配和排期计算；返回候选、得分与算法解释，不拥有正式策划结果的写入权 |

当前 Java 普通人工策划已在 `strat_matrix_bus` 保存任务、批次、明细和换题记录。旧自动策划及历史结果仍在 Python 库中，Java 的 `ManualPorts.Transition` 暂时联合查询。因此“页面已从 Java 返回”不等于“所有结果都已迁入 Java”。

## 本轮已改

1. 正式明细按 `批次 ID + 槽位 ID` 唯一。同一账号在同一周批次可有周一、周三、周五等多条结果；原来的 `批次 ID + 账号 ID` 唯一约束会阻止这种数据。
2. Java 新建结果写入 `slot_id`。已有行通过明细快照中的 `slot_id` 回填；没有槽位编号的旧行使用 `LEGACY-主键`，不改变原结果 ID 或 JSON 快照。
3. 批次详情、按新批次查策划与导出、单条换题候选改为按主键或批次读取，避免先加载 Java 全部正式明细。
4. 批次的“完成内容生产账号数”改为该账号的**所有槽位**完成才计入。槽位完成数仍按条统计。
5. 结果表字段含中文注释，账号＋日期及批次＋日期增加索引；多槽位与完成统计有隔离测试。

## 已有业务库升级

新建数据库使用 `java-backend/godp-planning-services/src/main/resources/db/manual-business.sql`。已存在 `godp_planning_item` 的数据库必须执行 `java-backend/godp-planning-services/src/main/resources/db/migrations/V3__result_slot_identity.sql`，`CREATE TABLE IF NOT EXISTS` 不会修改旧表。执行前核对业务库名、备份表结构与数据，并检查旧行的 JSON `slot_id` 在同批次内不重复。迁移完成后才能部署依赖新列的 Java 版本。

本地启动配置当前连接阿里云 RDS 上的 `strat_matrix_bus`。本轮只读预检结果为 **1 条旧明细、旧唯一索引存在**；没有修改该远端表，也没有重启正在使用旧结构的服务。迁移脚本仍待按目标环境发布流程执行。

## 继续迁移的顺序

1. **统一正式结果写入**：自动周策划、热点 T-1、营销衔接都由 Java 校验算法提案并写入业务库的批次与槽位；Python 不再写正式结果。
2. **历史结果过渡**：对旧 Python 结果确定一次迁移或只读归档方案。过渡期继续保留 `Transition`，不得把两库结果都当作可写主库。
3. **列表查询落库分页**：账号列表、时间列表及报表目前仍将新旧结果聚合后分页，最大读取范围受过渡适配器限制。历史退出后按业务库索引实现 SQL 分页、聚合与权限过滤；不能直接对当前混合列表套 PageHelper。
4. **统一状态**：Java 负责策划状态和内容状态投影；内容方状态由行内查询接口读取，不能通过 Python 或页面伪造生产完成。

## 验收点

- 一个批次同一账号写入三条不同日期槽位，详情与导出均能看到三条。
- 只完成其中一条时，批次完成账号数仍为 0；三条都完成后才为 1。
- 新批次详情与按批次导出只读取该批次；旧历史入口仍可查看。
- 账号列表、时间列表的筛选、排序、分页、失败详情和导出，在历史迁移完成前维持现有页面契约。
