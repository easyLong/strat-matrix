# 页面数据链路与驻场接入核查

核查日期：2026-11-03。范围：AI策划配置及历史、非营销人工策划、人工营销策划、策划任务列表、策划结果账号列表和时间列表。

本文按当前代码与本轮只读接口核查整理。测试任务状态是核查时点快照，不代表真实内容系统已验收；本轮未触发内容生产、重新匹配或改写用户配置。此前自动策划验收见[全流程测试与行内接入对照](全流程测试与行内接入对照_V1.0_2026-11-03.md)。

## 1. 公共边界

```text
Vue三个业务页面
  → 行内Java业务服务：权限、业务校验、任务、正式结果、查询及导出
      → Java业务库 strat_matrix_bus
      → Python算法服务：生命周期、标签投影、计算任务
          → Python算法库 strat_matrix

账号、选题、内容等基础事实：Java资料适配层读取
  outside：run/bank-source-fixture.json
  inside：宿主实现SQL或已有服务查询
```

- Vue只访问Java。当前前端请求`/api/...`，由开发代理映射到Java的`/api/plan/...`。
- 两库分别由各自服务维护。Java经HTTP调用Python；Python需要行内资料时经Java资料接口获取。
- 基础资料不新增一套完整镜像表；正式任务中保存本次计算需要的冻结快照，供追溯和重试。
- 行内由宿主调度推进任务。行外本地脉冲是开发运行适配，不能作为驻场后的正式调度装配。
- 内容生产、审核和账号分配由内容侧执行，本项目读取内容事实并维护策划结果。

## 2. AI策划配置与历史配置

### 2.1 保存与查询

```text
编辑并保存页面配置
  → Java校验业务配置及当前版本，持久化待发布命令
  → Java调用Python算法配置命令接口
  → Python按命令编号幂等保存算法配置并返回版本
  → Java事务发布业务配置和完整组合快照
  → 页面读取当前配置、历史列表及版本详情
```

这不是跨库事务：Python已保存但响应丢失时，Java保留待发布命令，后续用同一命令重试，避免重复生成算法版本。页面历史只读取已完成的发布记录。

| 数据库 | 表 | 职责 |
| --- | --- | --- |
| Java业务库 | `godp_business_planning_config` | 当前策划日、调度日期时间、营销上限、热点占比 |
| Java业务库 | `godp_business_planning_config_version` | 业务配置历史 |
| Java业务库 | `godp_planning_config_release` | 跨服务发布状态、两侧版本关联及完整组合快照；页面历史的数据来源 |
| Python算法库 | `godp_strategy_config` | 生命周期、阶段目标、滚动窗口等算法配置；标签树以独立配置标识保存 |
| Python算法库 | `godp_strategy_config_version` | 算法配置和标签树各自的版本 |
| Python算法库 | `godp_algorithm_config_command` | 配置命令幂等记录和处理结果 |
| Python算法库 | `godp_system_config` | 模型、凭据和端口等运行参数，不属于页面配置历史 |

标签树当前独立保存版本，尚未纳入页面组合历史的快照和恢复范围。页面中的“保存配置”可能先后保存上述两类内容，不能宣称已具备含标签的整体原子保存与恢复。

### 2.2 本轮历史空白修复

- 用户保存已成功：核查时最新原始版本为19，历史接口返回15条记录，最新快照与当前配置一致。
- 原始版本1、3缺少调度、策划日和生命周期等部分字段；旧组件直接访问`planning_days.length`，导致整个列表渲染异常。
- 历史类型改为允许早期字段缺失，列表摘要、详情和差异比较兼容旧快照；缺失字段显示“未记录”，不填入当前默认值。
- 不完整版本允许查看，禁用整体恢复，防止将不完整对象作为当前配置提交。
- 本轮没有修改数据库、用户当前配置或历史记录。版本显示仍沿用现有连续展示编号，原始版本号用于接口提交。

### 2.3 驻场重点

部署两侧表和权限、迁入Java配置发布模块、接入可信操作人、配置Java/Python内网鉴权与超时、用宿主调度恢复未完成发布。重点验收页面当前值、算法执行值及新任务冻结值一致；本轮历史渲染验收不能替代这项全程验收。

## 3. 非营销人工策划

### 3.1 交互与落点

```text
填写任务名称和投放日期
  → 选择账号、选择多个非营销选题
  → 确认提交
  → Java再次查询资料，校验资格、日期占用、选题类型及有效期
  → 冻结账号、选题及算法版本，保存预览
  → Java事务创建业务任务和账号日期占用
  → 调度推进：Java向Python提交同一计算编号和冻结输入
  → Python持久化任务，服务内受控异步计算，返回状态/结果
  → 后续调度再次提交同一编号获取结果
  → Java校验结果并事务写入正式批次、明细、完成任务
  → 页面查询正式结果
  → 内容侧生产；Java查询内容状态，更新明细和批次进度
```

步骤中的“保存”只确认前端选择，最终提交时才创建业务任务。预览是后端校验与冻结步骤，接口不返回分配结果，不是页面上的分配预览。

账号、选题列表由Java读取事实，再把明确资料交给Python补充生命周期和已有标签等投影。提交时重新取得冻结资料，不能仅相信浏览器携带的数据。

当前普通人工计算是在已选选题中，按任务编号作为随机种子，为每个账号选择1条，重试结果一致。它不是自动策划的V19召回、模型精判及全局求解，也不保证每个已选选题一定被使用。

### 3.2 涉及表

| 数据库 | 表 | 用途 |
| --- | --- | --- |
| Java业务库 | `godp_manual_preview` | 冻结输入及预览有效期 |
| Java业务库 | `godp_manual_task` | 持久化业务任务、执行状态和失败原因 |
| Java业务库 | `godp_manual_reservation` | 账号＋日期占用；并发提交防重，失败释放 |
| Java业务库 | `godp_planning_batch` | 正式批次及内容进度 |
| Java业务库 | `godp_planning_item` | 账号、日期、选题、快照及内容状态 |
| Python算法库 | `godp_manual_compute` | 冻结计算输入、状态、租约和结果 |
| Python算法库 | `godp_strategy_config`、`godp_topic_tag` | 资料投影读取的算法配置和已有标签 |

换题另写`godp_planning_adjustment`；内容状态对账更新原批次和明细。正式使用次数从内容已完成且存在内容ID的明细统计，不按提交次数统计。

### 3.3 本轮人工测试观察

“测试非营销流程”选择10个账号、2个选题，业务批次`1000000000001`已形成，10条正式策划；核查时策划已完成，内容待生产、完成账号0/10。选题数2是任务所选数量，实际用题以正式明细为准。

### 3.4 驻场重点

替换资料读取、接入UM和数据权限、发布任务与结果表、接通计算HTTP鉴权、用宿主调度推进与恢复、衔接真实内容状态。验收重复提交、同日账号冲突、失效选题、网络中断恢复和最终内容完成计数。

## 4. 人工营销策划

### 4.1 交互与落点

```text
填写任务名称 → 单选选题 → 填写生成内容数量 → 确认提交
  → Java查询并冻结选题资料，幂等保存营销需求
  → 内容侧读取需求，执行生产、审核和账号分配
  → Java查询生产进度，更新任务完成数、失败数、账号数
  → Java另行查询当前需求的过审内容＋账号分配
  → 补充并校验账号资料，安排投放日期
  → 写入正式批次、明细、资源占用和操作记录
  → 前端查询正式策划
```

- 创建时不选择账号和日期，生成数量是内容条数，不能直接等同于账号数。
- 当前创建接口只落需求，不自动调用内容Agent；内容侧消费方式须驻场联调明确，不能把“需求保存成功”视为“生产已开始”。
- 内容侧返回的进度、过审内容和账号分配，均需关联原营销任务编号。
- 生产完成与过审可排期是两个事实通道；任务显示完成不必然说明所有正式策划已经形成。
- 排期按过审时间升序，依照允许策划日、当天有效营销投放、营销周上限查找日期；当前从北京时间当天向后最多查找56天。找不到日期时保持未关联，等待后续扫描。
- 过审内容已经生产完成，形成正式明细时引用内容ID并记为内容完成，不再执行普通人工分配或V19匹配。

### 4.2 涉及数据

| 位置 | 数据 |
| --- | --- |
| `godp_manual_marketing_task` | 名称、原选题ID及快照、生成数量、生产进度、已关联数量、正式批次关联 |
| `godp_planning_batch`、`godp_planning_item` | 完成账号分配和日期安排后的正式结果 |
| `godp_planning_resource_claim` | 防内容重复引用、同账号日期冲突及营销周额度重复占用 |
| `godp_planning_adjustment` | 引用过审营销内容、确定日期的操作记录 |
| Java业务配置 | 策划日及营销周上限 |
| 内容侧事实 | 需求生产进度、内容ID、标题正文、二级类型、过审时间、分配账号及有效投放记录 |

行外由`marketing_results`、`marketing_allocations`、`placements`等模拟集合提供后续事实，不会因页面新增需求而自动生成这些事实。

### 4.3 本轮人工测试观察与驻场重点

“营销测试”选1个选题、生成数量10；核查时待分配、完成0/10、无正式批次。模拟资料没有此任务对应的生产或过审分配结果，因此等待是当前实际状态，不代表已跑通生产后半段。

驻场主要工作是需求交付内容侧、任务编号关联、进度和过审分配两类查询、账号资格及有效投放查询、宿主排期调度。资料查询和工程迁入复用公共接入边界。

## 5. 策划任务列表

```text
Vue点击查询／翻页
  → POST /api/plan/query/manual-tasks
  → Java校验分页和筛选条件
  → MyBatis查询 godp_planning_task_read
  → 返回当前页、总数、页码和每页数量
```

- 筛选：批次名称/编号、投放起止日期、创建人、内容状态；默认发起时间倒序，再按记录标识倒序。
- 视图组合`godp_manual_task`、关联的`godp_planning_batch`、`godp_manual_marketing_task`和旧任务归档`godp_planning_task_archive`。视图不复制数据。
- 列表按业务任务状态补充进度；查询本身不调用算法或启动生产。
- 进行中任务在当前页时，页面每3秒重查。该行为只刷新展示，不替代宿主任务推进或内容状态对账。
- “查看策划”有正式批次时复用批次策划详情；未关联批次的营销需求显示需求选题和数量详情；返回保留列表页码与筛选。
- 未安排投放日期的营销需求不满足指定投放日期范围筛选，不能将其自动填成创建日期。

驻场重点：业务查询模块和视图发布、可信创建人和数据权限、真实内容状态查询、分页与筛选验收。

## 6. 策划结果：账号列表、时间列表

### 6.1 账号列表

```text
POST /api/plan/query/accounts
  → 正式明细按账号去重、筛选和SQL分页
  → 读取当前页账号的明细快照
  → 补充当前基本资料，保留已有派生字段
  → 返回列表及筛选选项
  → 查看策划：/query/plans，限定account_id
```

列表只包含已有正式策划的账号，不是全部基础账号。资料补充可能经Python算法投影，但不会重新匹配或生成策划。当前按账号最近批次创建时间倒序、账号ID排序；详情使用冻结资料，不改写历史输入。

### 6.2 时间列表

```text
POST /api/plan/query/periods
  → 按正式批次所属自然周筛选、分页
  → 查询本页周期下批次和账号内容完成情况
  → 返回周期和批次集合
  → 展开批次／查看周期或单批次策划
  → /query/plans限定周期、批次ID范围
```

时间列表按周起始日期倒序；周期内批次按创建时间和ID倒序。起止日期筛选目前用于选取覆盖的批次归属周，不等同于逐条投放日期精确裁剪。详情中的日期筛选另作用于正式明细的投放日期。

### 6.3 数据来源与去向

| 数据 | 来源 |
| --- | --- |
| 周期、批次、策划方式及批次进度 | `godp_planning_batch` |
| 账号、选题、投放日、快照及内容状态 | `godp_planning_item` |
| 账号基本资料补充 | Java当前资料查询 |
| 失败账号及原因 | `godp_planning_failure` |
| 调整记录、报表最新操作 | `godp_planning_adjustment` |
| 查询视图 | `godp_planning_item_read`、`godp_planning_batch_read`，由MyBatis筛选、分页和聚合 |

查询结果返回Vue，不新增业务任务。概览和12类分布按全筛选范围统计，分页只控制详情加载范围；同一选题在同一二级类型下只计一次。

自动策划经Java正式提交、普通人工经Java校验计算结果、人工营销经内容引用及排期后，统一进入正式表。只有营销需求而无正式结果时，不会出现在正式策划列表中。

核查时账号列表96个账号；2026-11-02～11-08周期下4个批次，包含本轮非营销测试。这是核查快照，不是初始化数量要求。

### 6.4 驻场前待收口

1. **账号筛选与展示依据**：当前组织、粉丝量等SQL筛选使用策划快照，展示又补充最新基本资料，资料变化后可能不一致；需统一实时/历史查询口径后再验收。
2. **统计口径**：账号数按周期去重，失败数当前汇总各批次`failed_count`，完成数按账号数减失败数推算；同一账号跨批次出现失败时可能重复计数，应收口到账号级失败与完成规则。
3. **默认状态**：账号列表接口当前返回固定`latest_status=已完成`，不能把该字段解释为账号内容已全部生产完成；若页面使用，需明确实际含义和计算来源。
4. **生产与排期**：营销生产完成、过审可排期、全部引用完成需分别验收；普通内容状态依赖真实内容事实对账。
5. **权限和性能**：宿主数据权限须同时覆盖列表、详情、失败导出和报表；发布视图与索引，核查真实规模下的JSON字段筛选和分页性能。

以上为已识别事项，本轮只修复配置历史渲染，没有更改这些业务查询和统计逻辑。
