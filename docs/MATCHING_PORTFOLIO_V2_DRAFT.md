# V2 策划组合目标与 MMR 方案

状态：**组合目标与搜索已接入独立 V2 执行器；权重仍为待评估起点，必须在专属策略中显式填写并批准后才运行**。实现位于 `backend/app/matching_portfolio_v2.py` 与 `backend/app/matching_executor_v2.py`。

## 1. 目标函数

先分别计算每个账号的组合指标，再对账号等权平均，避免槽位较多的账号在目标函数中占更大权重：

```text
U = 0.55 × R + 0.20 × C + 0.10 × B − 0.15 × D
```

各项均归一化到 `[0, 1]`。权重合计为 1。首轮用这组比例比较算法结果，不视为已校准的生产值。

### 相关性 R

```text
R_account = 该账号已分配槽位 Fit 分数之和 ÷ 该账号计划槽位数
R = 所有账号 R_account 的平均值
```

当前接入执行器使用冻结账号/选题向量的 cosine Fit，范围 `[0, 1]`；这与未来的 T1–T6 多特征 Fit 是不同阶段。未分配槽位按 0 计入分母，避免少分配槽位却获得虚高的平均分。所有账号等权，不因某账号槽位数量多而获得更大的相关性权重。

### 覆盖度 C

对每个账号分别计算 T3 主题域、T4 目标客群、T5 生活场景的覆盖比例：

```text
C_d = 该维度已覆盖的不同稳定叶子标签数 ÷ 该账号计划槽位数
C_account = (C_T3 + C_T4 + C_T5) ÷ 3
C = 所有账号 C_account 的平均值
```

同一账号一周 3 个槽位若覆盖 3 个不同主题域，T3 覆盖为 1；只有 2 个不同主题域，覆盖为 2/3。T3/T4/T5 使用冻结 taxonomy 版本下的稳定叶子 ID；分类父级不重复计作新的覆盖项。未分配槽位降低覆盖度。由于准备阶段要求选题 T1–T6 完整，已分配选题缺少 T3/T4/T5 稳定 ID 属于输入错误，不按空标签略过。

### 平衡度 B

平衡度衡量同一个账号各槽位的 Fit 是否差距过大，不再重复计算 T2 流量/转化比例。T2 经营作用比例由冻结生命周期策略和槽位角色另行约束。

```text
B_account = max(0, 1 − (该账号槽位最高 Fit − 最低 Fit))
B = 所有账号 B_account 的平均值
```

未分配槽位 Fit 按 0 参与范围计算；空组合的平衡度为 0。该指标表达“避免把一个槽位牺牲得很差”，不能替代相关性 R。

### 冗余度 D

```text
D_account = 该账号已分配选题的两两语义相似度平均值
D = 所有账号 D_account 的平均值
```

相似度使用冻结 `semantic_space_id` 下的同一向量空间，范围 `[0, 1]`。一个账号少于两个已分配选题时，冗余度为 0。此指标只在账号内部计算，避免不同账号的选题相似被误判为同一账号内容重复。

## 2. MMR 的定位

MMR 是**候选缩减和初始组合构造的近似搜索步骤**，不是最终目标函数中的第五个加分项。候选排序使用：

```text
MMR(topic) = λ × Fit(topic) − (1 − λ) × max_similarity(topic, 已暂选选题)
```

初始 `λ = 0.70`，模板每槽位先召回 Top-K=100，再由 MMR 保留最多 20 个候选。每个账号按投放日期顺序，暂选最高 MMR 选题作为后续槽位的去重参照；同时保留其余候选供全局搜索调整。召回数必须大于 MMR 保留数，避免配置成相同数量时 MMR 形同虚设。

全局目标里的 `D` 已对最终组合惩罚冗余，因此 MMR 排序分**不会再加到最终效用**，避免重复惩罚。MMR 只影响搜索候选范围，最终方案按 `U` 评价。

## 3. 搜索方法与约束

当前草案先以可解释的确定性局部搜索实现：

1. 从容量约束矩阵分配结果作为初始方案；
2. 在 MMR 保留的候选边中，尝试单槽位换题、释放槽位，以及两个槽位互换选题；
3. 每次选择使全局组合分提升最多的合法变更；
4. 直到没有正向单步或双槽变更，或达到策略中的迭代上限。

每次变更都遵守：每槽位最多一个选题、同账号周期内选题复用上限、每个选题的全局容量。双槽交换可以跨账号，但每个账号的复用上限仍会重新校验。相似度在一次优化运行中按无序选题对缓存，减少重复向量相似度计算。当前做的是局部最优近似，不承诺数学上的全局最优；更大规模的多槽联合变化可进一步评估整数规划求解器，并在同一离线样本上比较收益和耗时。

## 4. 首轮评估参数草案

参数与数据版本必须写入 V2 策略及任务审计：

```json
{
  "relevance_weight": 0.55,
  "coverage_weight": 0.20,
  "balance_weight": 0.10,
  "redundancy_weight": 0.15,
  "mmr_relevance_weight": 0.70,
  "shortlist_per_slot": 20,
  "max_improvement_passes": 25
}
```

另需显式提供 `same_account_same_cycle_max` 与每个选题的全局容量策略；这两个字段不在此处自动补默认值。跨账号容量可明确设为不设硬上限，也可按选题配置容量。

这套参数应在冻结的账号/选题样本上与 V1 及纯 Fit 基线对照，重点检查：平均 Fit、每账号 T3/T4/T5 覆盖、账号内冗余、未分配槽位数、各槽位 Fit 差距、人工接受率和运行耗时。根据人工评审调权重后再冻结策略版本。

离线评估还应测候选缩减召回：对比 shortlist 20 与全量候选产生的最优可行结果差异，并记录因剪枝而错过的高效用组合。若业务样本显示差异明显，应扩大 shortlist 或使用逐步扩展候选集，不能只靠提高迭代次数弥补被剪掉的候选。

## 5. 实现限制

- `matching_portfolio_v2.py` 已实现参数校验、MMR 候选缩减、账号等权的四项组合分计算，以及容量约束下的单槽改进与双槽交换；`matching_executor_v2.py` 已接入独立 Worker 路由。
- 当前 V2 沿用已批准 cosine 候选契约；账号侧 T3/T4/T5 映射和多特征 Fit 仍按[策略契约草案](MATCHING_POLICY_V2_CONTRACT_DRAFT.md)待建设。不得把当前生产适配描述为完整 T1–T6 账号标签匹配。
- V1 的五阶段审计格式、`builtin-cosine-balanced-v1` 执行器和已保存策略不变。
- Worker 只领取绑定 V2 实现标识且已批准策略的任务；保存结果仍是匹配提案，不直接写正式策划批次。
