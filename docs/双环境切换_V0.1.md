# 双环境切换 V0.1

日期：2026-11-03；配置来源澄清更新：2026-11-11。统一名称：**outside：行外模拟接入；inside：行内宿主接入**。

## 配置来源与切换边界

独立开发部署通过`godp_system_config.PLANNING_ENV`选择模式，值只允许`outside`或`inside`。这不是三个宿主工程共用的动态切换表；嵌入行内后各宿主拥有配置来源，不要求Java启动时访问Python算法库。

| 配置 | 独立行外部署 | 行内宿主接入 |
| --- | --- | --- |
| Python环境与模型 | `godp_system_config` | `PlanningConfig.settings`显式值优先，其次宿主`settings_provider()`或算法库配置 |
| Java运行环境 | 本地启动器读库判断是否启动outside开发壳；生成Spring profile配置 | 在宿主已有profile中追加inside，并由宿主配置中心管理 |
| Java数据库与事务 | 开发数据源和配置生成器 | 宿主提供的MyBatis会话、业务事务及资料数据源 |
| Java的Python地址及令牌 | 本地启动器生成的私有配置 | `planning.python.base-url/token`或宿主运行时配置提供者 |
| Vue请求地址、权限 | 本地开发装配 | 复用宿主Axios、路由、会话与权限；不读模型配置表 |

数据库账号仍由各环境自己的`.env`或宿主数据源注入。独立部署的模型、端口、地址和鉴权仍保存在算法库；行内允许宿主显式注入连接参数，不改变算法规则、标签和策略仍归Python维护的边界。

**环境切换与模型协议切换是两个选择。**`PLANNING_ENV`决定资料/宿主接入；`MODEL_PROTOCOL`决定文本请求协议。`chat_completions`用于既有兼容服务，`doubao_native`用于本次行内请求格式，具体见[行内模型网关](../python-backend/BANK_MODEL_GATEWAY.md)。二者不隐式绑定，Java不负责转换模型协议。

| 部分 | outside | inside |
| --- | --- | --- |
| Vue | 本地Java入口，未配置时使用6931回环地址 | 必须指定宿主Java入口，不能退到Python或本地Java |
| Java | outside profile装配已有local开发壳和模拟接入 | inside profile关闭开发代理、本地调度及运行期建表；宿主提供业务数据源和端口实现 |
| Python资料源 | Java HTTP；Java读取本地模拟文件 | Java HTTP；Java查询行内表/服务 |
| 调度归属 | 本地Java模拟宿主任务 | 客户现有调度；Python不自行触发业务调度 |
| 内容生产 | 可显式使用行外测试方式 | 禁止`CONTENT_PRODUCTION_MODE=local_mock` |
| 数据库 | 行外独立业务库、算法库 | 行内独立业务库、算法库，Java读取行内事实；Python不直连行内业务库 |

业务服务、算法及页面不维护两份。日常开发和完整验收已收口到相同Java资料入口；Python不再直接读夹具。原始资料在Java读取，生命周期/标签等算法投影仍由Python计算。见[统一资料链路](统一资料链路_2026-11-03.md)。

## 操作命令

在`python-backend/`目录执行：

```bash
# 查看当前模式，兼容旧部署时会显示compatibility_mode=true
python -m app.content_planning.deployment_environment show

# 检查当前配置，或预检inside，均不修改数据库
python -m app.content_planning.deployment_environment check
python -m app.content_planning.deployment_environment check inside

# 选择目标环境，只写PLANNING_ENV，不复制数据、不改地址和密钥
python -m app.content_planning.deployment_environment select outside
python -m app.content_planning.deployment_environment select inside
```

`inside`预检要求`JAVA_GATEWAY_URL`、`JAVA_API_BASE_URL`、`JAVA_API_TOKEN`和`INTEGRATION_TOKEN`有效，且关闭本地内容模拟。校验失败时不更新选择项，不输出密钥。预检只检查配置，不证明宿主SQL、认证和网络已经接通。

模式是**部署选择**，不是运行中的页面切换按钮。各环境使用独立配置和数据，升级时先停止业务执行，设置模式后重新生成本地启动配置并重启服务，避免执行中的任务中途换源。切换不会搬迁数据、清空数据或替代数据库版本发布。

## 启动与驻场

- `start.sh`读取库内模式并预检；outside构建最新Java包、生成带outside profile的私有启动配置，启动本地三服务；inside不启动本地Java开发壳。
- Java当前默认Spring profile为`dev`，`dev`和`outside`均通过profile组复用`local`；本地启动器显式使用`outside`。inside与local同时误启时，本地数据源、调度和代理类也不会注册。
- 新生成的本地配置显式开启业务和业务配置模块；裸Java开发壳仍可不连库启动，不能把壳的存活当成业务已就绪。
- 驻场将业务包、Mapper和配置片段并入客户三个工程，客户负责绑定真实资料、内容事实、身份、事务及调度。不复制`standalone`启动壳或本地适配器。
- inside/outside是本模块的模式，不替代客户现有dev/test/prod环境体系；最终按宿主要求合并配置。
- 第一次行内适配完成后，日常主要替换环境配置和发布变更模块；配置选择不会自动生成未知行内表的SQL，也不会自动接通行内模型服务。

## 旧开关迁移

没有`PLANNING_ENV`时，继续解释旧`JAVA_ACCESS_MODE`和`BANK_SOURCE_MODE`。初始化新增模式时，已有bank或Java HTTP部署会保持inside方向，不会因默认outside退回模拟。

明确设置`PLANNING_ENV`后，旧两个模式项只作为兼容数据保留，新运行路径使用统一选择。升级不要只更换启动配置而继续复用旧jar；应一起发布本轮代码、profile和配置生成器。
