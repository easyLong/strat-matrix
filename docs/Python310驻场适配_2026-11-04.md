日期：2026-11-04。客户已确认行内Python版本为3.10.11，本项目以该版本作为交付及测试目标。

根目录及`python-backend/.python-version`记录3.10.11，供版本管理器使用；文件本身不会切换系统Python。生产安装使用`requirements.txt`，开发测试使用`requirements-dev.txt`。这些文件锁定直接依赖，尚不等于完整传递依赖锁文件。

## 修复内容

1. 全新3.10.11环境安装原清单后，发现缺少时区数据及测试客户端依赖。已补`tzdata`和开发依赖`httpx2`，固定Starlette到已验收版本，避免无上界依赖自动选择其它版本。
2. 固定测试数据生成器改用`math.fsum`计算向量归一化。Python3.10与较新版本的浮点`sum`实现差异曾造成测试数据末位不同；现有small/scale数据指纹、V19基线及业务算法没有被重写。
3. 驻场交接包包含`python-backend/.python-version`，与依赖清单一并传递目标版本。

## 验证结果

- 工作区内独立Python3.10.11及`python-backend/.venv`，未使用全局3.14的site-packages。
- 按`requirements-dev.txt`全新安装完成，`pip check`无依赖冲突。
- 260个Python文件通过3.10语法检查（后续新建虚拟环境目录不属于源代码检查范围）。
- 最终完整回归：`run/regression/20261104-204009-517201/summary.json`为passed。
- Python471项及149子测试、工具43项、V19固定回放、Java测试、前端29项和类型检查/构建均通过。
- 无真实模型调用，无正式业务数据写入；此轮未切换或重启现有日常运行服务。

前两次失败报告保留在run目录：第一次暴露干净环境的依赖遗漏，第二次只剩跨Python版本的测试向量生成差异。最终修复后六步完整回归全部通过，不通过覆盖旧报告或重录基线消除失败。

## 使用目标环境

行内先确认`python --version`为3.10.11，然后在`python-backend`目录创建独立环境。Linux示例：

```bash
python3.10 -m venv .venv
. .venv/bin/activate
python --version
python -m pip install -r requirements-dev.txt
python -m pip check
```

本Windows工作区可在仓库根目录直接使用已准备的环境：

```powershell
.\python-backend\.venv\Scripts\python.exe --version
.\python-backend\.venv\Scripts\python.exe -m testing --suite python
```

运行API时切到`python-backend`后，用激活环境的`python -m uvicorn app.main:app --host 127.0.0.1 --port 6930`。已有运行服务切换应单独安排，避免与原端口重复启动。

驻场仍需确认目标操作系统、CPU架构、模型网关及离线包来源。Windows安装验收不替代行内Linux离线安装验收；尤其Pydantic Core需匹配目标CPython3.10及平台的wheel，不复制Windows虚拟环境到Linux。
