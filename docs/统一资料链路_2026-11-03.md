# 日常开发与完整验收统一资料链路

日期：2026-11-03。

## 1. 现在只有一个取数方向

```text
Vue ──→ Java业务服务 ──→ Python算法服务
             │                 │
             │         Java资料查询HTTP
             │                 ↓
             └────── Java SourceFacts
                         │
                  outside：模拟文件
                  inside：行内SQL/服务
```

Java基础资料查询不会调用Python，避免循环调用。页面账号需要生命周期、选题需要标签时，Java将已经查出的实体传给Python的`catalog-projection`计算；该能力仅读取算法配置/扩展，不再发HTTP取基础资料。

这保留“Java管业务，Python管算法”的边界，没有把生命周期、标签和映射搬到Java，也没有新建一套基础资料同步表。

## 2. 代码与职责

| 位置 | 职责 | 行内如何处理 |
| --- | --- | --- |
| `planning/source/SourceFacts` | 账号、选题、营销内容、有效营销投放、内容/营销状态的原始查询边界 | 提供行内SQL/现成服务实现 |
| `SourceFactsController` | 统一内部HTTP查询和鉴权；使用次数调用Java业务聚合 | 可保留路由与对象；按宿主鉴权、响应包装适配 |
| `adapter/local/FixtureSourceFacts` | 直接读取同一模拟文件，支持分页、ID、来源、类型、更新时间、有效期 | 不迁入行内，替换为真实查询 |
| `adapter/local/OutsideSourceAdapter` | 页面/人工策划需要的Source：读取Java资料，再发算法投影 | 行内由既有`HostSourceAdapter`及各资料端口装配，可复用算法客户端 |
| `FixtureContentObservations` | 从同一模拟资料入口读取明确提供的内容/营销状态，再关联本次明细版本；缺事实不伪造完成 | 替换为行内内容事实查询 |
| `CatalogProjectionPythonClient` | 把明确实体交Python派生算法字段 | 可复用，按宿主HTTP客户端要求适配 |
| Python `JavaHTTPSource` | 通过Java查询并强校验实体/分页/资格 | outside与inside共用；配置地址、鉴权与必要字段映射 |
| Python `services/catalog_projection` | 对请求中的实体计算生命周期、趋势及附加标签 | 算法侧保留；不读本地文件、不请求资料HTTP |
| `LocalPythonAdapter` | 仅保留计算提交和旧业务历史兼容 | 当前正常历史查询已关闭旧桥；不作为资料来源 |

## 3. 查询地址与配置

日常地址默认：`http://127.0.0.1:6931/api/plan/internal/source`。

| POST相对子路径 | 能力 |
| --- | --- |
| `accounts/query` | 账号分页，参与资格、ID列表、更新时间范围 |
| `topics/query` | 选题分页，ID列表、普通/热点、营销/非营销、更新时间、可用性和有效时点 |
| `marketing-contents/query` | 账号已过审营销内容 |
| `effective-marketing/query` | 账号指定日期有效营销投放 |
| `production-status/query` | 明细生产事实 |
| `marketing-status/query` | 人工营销需求进度 |
| `marketing-allocations/query` | 人工营销需求对应的过审内容及账号分配，缺实现时明确拒绝 |
| `topic-usage/query` | Java正式明细聚合的累计使用次数 |

资料DTO和请求的中文别名沿用现有契约，未重新定义客户业务字段。稳定ID排序；更新时间范围左闭右开；不符合参与资格的账号不返回。没有模拟文件、重复ID、异常分页、错误鉴权时明确失败，不降级为另一套资料源。未提供的模拟内容事实返回空列表，不能当成生产完成。

明确`PLANNING_ENV`后，outside/inside均固定使用`java_http`。outside允许未填写`JAVA_API_BASE_URL`时从`JAVA_GATEWAY_URL`推导上述默认前缀，未填写`JAVA_API_TOKEN`时复用`INTEGRATION_TOKEN`；inside仍必须显式配置真实地址和令牌，不回退到本地。旧部署没有选择项时仍保留旧开关兼容解释，升级应明确选择outside或inside。

本地配置生成器写入`planning.source.enabled`、`planning.source.fixture`和`planning.source.token`。凭据只在忽略的私有启动文件内，不提交、不在进程参数打印。修改后需重新生成Java配置并重启。

旧Python `POST /api/internal/manual-source`返回410，不能继续作为取数入口。历史操作记录等兼容查询不在这次资料收敛中擅自删除。

## 4. 日常与完整验收的区别只在测试控制

日常开发直接运行三个正常服务，90个账号和57个选题仍在同一`run/bank-source-fixture.json`中。修改文件后Java下次读取即可看到，不需要重启资料服务器。

`python -m testing.live --execute`先检查日常Java资料入口，再原子追加独立测试ID资料，不覆盖其他记录。使用同一个Java入口，不再启动临时Java HTTP资料服务器；Java测试驱动仍用于模拟时钟、确认丢响应和内容观察，隔离的Python计算进程只限制本轮账号/选题ID，不改变资料协议或模型算法。

完整验收仍会调用真实模型并写当前两个开发库；它不是物理隔离的测试库。执行前仍需暂停日常调度、排空无关任务，结束后恢复。失败资料保留供排查；同ID不同资料拒绝覆盖。当前尚未自动暂停/恢复，也没有自动清理测试资料。
