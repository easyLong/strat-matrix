# V19 算法统一说明

自本次修改起，普通选题自动匹配仅运行 V19。行内、行外使用相同算法代码，环境选择仅决定数据接入方式。

## 唯一执行链路

冻结账号、选题及配置 → 账号正式映射 → 选题主关联标签 → 五路召回 → 模型配对精判 → 经营作用与有效期约束 → 组合分配 → 校验提案 → Java 落正式业务结果并确认。

`matching_quality_executor.py` 是唯一执行器。已删除旧 `matching_executor.py` 与 `matching_executor_v2.py`；公共分配及组合计算分别命名为 `matching_allocation.py`、`matching_portfolio.py`，由 V19 复用。

五路召回、精判阈值、映射版本与组合权重仍受不可变策略版本管理，并非保留多套算法。当前尚未单独实现独立7–8条候选池、历史T2补缺与两阶段求解，保持原V19实现的能力边界。

## 执行和历史边界

- 新策略、新匹配任务及自动策划入口仅接受 V19；Worker 只领取 V19 任务。
- 旧策略停用，旧待执行任务标记 `algorithm_retired`；历史提案、输入、报告、业务批次与操作记录保留，指纹不改写。
- 旧任务需重新准备输入并绑定 V19，不能修改旧输入或策略指纹后继续运行。
- `evaluation_only=true` 仍为仅评估策略，禁止正式提交；正式策略显式设为 `false`，并且只能使用审核映射。
- 正式提案继续检查精判证据、模型/输入/策略指纹、租约和容量；未匹配位置不能通过降低精判门槛或热度兜底伪造成功。
- 算法与业务职责、双库隔离、Vue→Java 及宿主调度方式保持现有约定。

## 已有环境升级

在 `python-backend` 下执行：

```bash
python -m app.consolidate_v19
python -m app.consolidate_v19 --apply
```

第一条只检查；第二条从已批准 V19 策略复制一个正式版本，保留模型、映射、门槛与权重，绑定 `AUTO_PLANNING_POLICY_ID`，停用旧算法策略并结束旧待执行任务。存在旧算法有效租约时拒绝切换。工具可重复执行，不删除业务数据；完成后重启 Python 服务以移除进程内旧执行器。

新环境没有已批准 V19 策略时工具明确失败，需先建立并批准真实策略，不能直接用合成测试策略替代。

新建策略可参考 `docs/examples/matching-policy-v19-quality-v1-template.json`。模板不预设向量空间，必须填写实际模型、维度与语义空间后才能批准。

本地环境已完成切换：原绑定策略5改为正式V19策略9，沿用已批准V19策略8的参数，仅将用途由评估切为正式；旧策略1和5停用。20条已有匹配任务均保留，没有待执行旧任务需要失效处理。Python服务已重启，Java结果查询仍返回89个账号、19个周期。

## 行外验证

```bash
python -m testing --suite algorithm --dataset small
python -m testing --suite algorithm --dataset scale
python -m testing
```

小集为5账号、60选题、15个匹配位置；规模集为100账号、600选题、300个位置。仅执行 V19，与保存的 V19 基线比较。报告包含匹配明细、约束、精判和选题变化，不再生成 V2/V19 对照。合成回放不调用真实模型、不写业务库，不能代替真实模型质量验收。

基线为 `testing/baselines/small-v19.json` 与 `scale-v19.json`。数据版本为 `planning-synthetic-v19-1`，旧双算法报告保留在原本的验收目录中，不作为新版本基线。
