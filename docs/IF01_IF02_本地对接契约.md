# IF-01 / IF-02 本地对接契约

依据《多账号智能策划_PRD_V1.0.docx》第 8.2.1～8.2.2 节。客户最终技术协议尚未提供；当前项目提供受 `X-Integration-Token` 保护的 HTTP JSON 入口。令牌配置在项目根目录 `.env` 的 `INTEGRATION_TOKEN` 中。

## IF-01 账号与近三个月帖子级互动

`POST /api/integrations/accounts/sync`

```json
{
  "source_batch_id": "ACC-20261008-001",
  "mode": "incremental",
  "records": [
    {
      "account_id": "ACCOUNT-001",
      "account_name": "账号名称",
      "account_alias": "运营别名",
      "account_status": true,
      "certification_status": true,
      "account_persona": "本地生活与家庭消费内容定位",
      "is_marketing_account": false,
      "account_tags": ["本地生活", "家庭消费"],
      "follower_count": 12000,
      "interaction_data": [
        {
          "content_id": "POST-001",
          "published_at": "2026-10-07T12:00:00+08:00",
          "title": "近期内容标题",
          "red_star_count": 50,
          "favorite_count": 20,
          "comment_count": 10
        }
      ],
      "updated_at": "2026-10-08T01:00:00+08:00"
    }
  ]
}
```

`interaction_data` 是该账号本次同步的完整帖子级近三个月数据；传 `[]` 表示确认没有历史帖子，省略该字段则继续使用既有独立历史内容同步记录。单篇互动量为红星、收藏、评论数之和。有效内容数只统计发布时间在当前时间至前三个自然月之间的帖子；滚动篇均互动取最近 X 篇的平均值，X 来自经营策略配置。账号生命周期按已有五阶段条件从高到低命中，计算值随周策划账号快照保存。

手动策划的流量趋势取最近 X 篇与再前 X 篇的篇均互动比较：前一窗口为 0、当前窗口大于 0，或增长至少 20% 为“上升”；下降至少 20% 为“下滑”；其余为“平稳”。不足 2X 篇显示“数据不足”。流量趋势由本项目计算，不由客户系统单独提供。别名可用于手动策划账号搜索。

老接口字段 `persona`、`marketing_eligible`、`followers`、`certified`、`enabled` 继续兼容；对应正式字段有值时以正式字段为准。每条账号记录仍须提供带时区的 `updated_at`，用于本地增量去重。相同账号和更新时间、不同内容返回 409。

## IF-02 普通选题

`POST /api/integrations/topics/sync`

```json
{
  "source_batch_id": "TOPIC-20261008-001",
  "mode": "incremental",
  "records": [
    {
      "topic_id": "TOPIC-001",
      "title": "普通选题标题",
      "outline": "核心内容大纲",
      "content_type": "图文",
      "topic_heat": 85.5,
      "status": true,
      "updated_at": "2026-10-08T02:00:00+08:00"
    }
  ]
}
```

`status` 是选题是否可用，兼容原 `enabled` 字段；`topic_heat` 是普通选题热度排序值。周策划与热点普通兜底只读取当前可用、当前有效的普通选题，按热度降序、选题 ID 升序排列。缺少 `topic_heat` 的旧数据按 0 处理。原接口允许同步营销选题的扩展字段，但正式营销选题应使用独立的 [IF-03 全量快照](IF03_营销选题同步契约.md)。

## 全量快照与增量更新

上述两个入口均支持 `mode=full`。全量请求可附带时区的 `snapshot_at`；省略时以服务端接收时间作为快照时间。`records` 表示该来源类型的完整集合，可以是空数组；一次最多 5000 条，因此 600 条普通选题可一次提交。IF-02 全量快照只能包含普通选题，营销选题仍由 IF-03 单独同步。

全量处理是一个事务：先校验批次 ID、快照时间和每条记录版本，再保存出现的记录，将此前存在但本次缺席的正式账号或普通选题标记为不在最新快照中，并停用对应目录项。`DEMO-` 演示数据和旧接口存入的营销选题不会被 IF-02 全量快照停用。成功返回的 `deactivated` 是本次停用数量；空快照会停用该来源类型全部现存正式记录，但不物理删除。旧策划批次的结果快照不受影响。

相同 `source_batch_id`、相同请求重传返回原结果；相同批次但内容不同、快照时间不递增或某条记录版本早于本地时返回 409，整批不生效。增量模式每批 1～500 条，仅更新本次出现且版本更新的记录，不停用缺席记录。停用后，只有更新版本的增量记录或后续包含该记录的成功全量快照会重新启用它。

本项目内部可用 `GET /api/internal/source-sync-status/account` 和 `GET /api/internal/source-sync-status/topic` 查询最近成功全量快照、接收数、停用数及当前可用数；这两个内部接口使用相同令牌，不属于客户数据同步接口。客户最终的分页、鉴权和传输协议仍待确认。

部署更新后运行 `(cd backend && .venv/bin/python -m app.init_db)`，创建带中文说明的全量运行表，并补齐账号与普通选题来源的快照标记字段。
