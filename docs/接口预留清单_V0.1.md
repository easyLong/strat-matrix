# 多账号智能策划数据归属与接口边界清单 V0.1

日期：2026-09-28。状态：根据现有原型和代码整理的接口设计建议，待后续 PRD 收敛；本文不会使接口自动生效。

本清单是 V0.1 预留接口资料，其中部分旧口径已被后续 PRD 修订。当前开发和联调以 [PRD V2.1 开发对照](./PRD_V2.1_开发对照.md) 及 PRD 原文为准。客户接收地址尚未提供，待投递事件保存在本项目数据库。实现与用法见 [README](../README.md)。

## 1. 依据与范围

- 客户页面基线：[运营前端原型](./多账号智能策划_运营前端原型_V1.0.html)，四个 Tab 为策划配置、AI 自动策划、手动策划、策划结果。
- 系统对接依据：[专项原型](./多账号智能策划_专项原型_V1.0.html)的“IT 系统对接”章节：三类输入同步、一套增量输出协议。
- 运营原型另外明确要求“生成完成状态回传”和“选题标签同步至选题库”，也必须纳入对接范围。
- 当前实现依据：[后端路由](../backend/app/main.py)、[接口模型](../backend/app/models.py)、[数据库结构](../backend/schema.sql)。

下面先按**归属和调用方**区分本项目内部数据、本项目前后端接口、与其他团队系统的接口，再区分“已实现”“需扩展”“建议新增”。新增 URL、请求字段英文名及传输方式属于建议，不代表已经通过评审。对外推送还是本系统定时拉取，需要根据客户系统能力确定；无论选择哪种方式，都保留相同的数据契约和本地同步记录。

### 1.1 三个层次，不能混为一类

| 层次 | 谁生产、谁使用 | 典型内容 | 是否需要其他团队对接 |
| --- | --- | --- | --- |
| 本项目内部数据与任务 | 策划后端、数据库、调度器之间 | 配置、标签判定、账号阶段、Fit、批次、槽位、草稿、快照、统计、任务和事件投递记录 | 否 |
| 本项目前端 ↔ 后端接口 | 四个 Tab 的浏览器页面调用策划后端 | `/api/config`、`/api/accounts`、`/api/batches`、周报、预览、替换等 | 否；由本项目开发 |
| 跨系统业务接口 | 策划系统与客户账号系统、选题库、历史运营系统、内容生产系统之间 | 输入同步、策划事件输出、生产状态回传、标签回写 | 是；需与接口提供方确定契约 |

例如账号资料先由客户账号系统通过**跨系统接口**同步，本项目把它保存为本地账号档案，再通过 `GET /api/accounts` 供手动策划页面使用。`GET /api/accounts` 是**本项目前后端接口**，不能当成客户账号系统需要提供的接口。选题和历史数据同理。

### 1.2 本项目内部运转的数据

| 内部数据 | 来源或计算者 | 在本项目中的用途 | 是否向外共享 |
| --- | --- | --- | --- |
| 账号本地档案 | 接收客户账号事实后形成的本地副本 | 硬性资格校验、筛选、策划 | 仅在策划结果/生产任务中发送必要字段 |
| 选题本地目录 | 接收客户选题事实后形成的本地副本 | 可用性、审核和有效期校验、匹配 | 输出选中的 `topic_id` 和必要上下文 |
| 历史运营数据本地副本 | 客户历史数据同步 | 滚动窗口、去重、生命周期与趋势计算 | 向外发送结果需要的摘要，不整体回传原始数据 |
| 运营配置与配置快照 | 运营人员经本项目前端保存 | 阶段条件、比例、回退规则、版本追溯 | 原则上留在本项目；对外事件可附所用配置版本 |
| 标签体系与选题标签 | T1–T5 由运营维护，T6 由本项目模型识别 | 策划匹配、筛选与内容生产输入 | 标签字典和选题标签按约定同步到选题库 |
| 账号阶段、Fit、评分、槽位算法状态 | 本项目计算 | 自动策划、占位与补齐、效果分析 | 真实内容就绪时发送必要 Fit/标签；内部占位计算值不发出 |
| 周期、批次、槽位、版本、调整记录 | 本项目生成 | 结果查询、替换、审计、去重 | 输出稳定槽位 ID、版本和必要结果事件 |
| 手动草稿、抽取结果、预览分配 | 本项目生成 | 页面恢复、预览和防止重复抽签 | 提交生产时只输出最终分配 |
| 内容状态、选题使用统计 | 本项目根据客户生产回传更新 | 状态显示、计数、结果汇总 | 可在策划结果中查询；状态事实以约定来源为准 |
| 同步任务、待发送事件、重试记录 | 本项目集成层保存 | 幂等、失败重试、对账 | 对接方只需按契约接收/确认，不需要访问内部表 |

“内部数据”不表示原始事实由本项目创造。账号、选题、历史内容由其他系统提供，本项目持有用于策划的本地副本；配置、规则计算、槽位和结果由本项目负责生成。数据库表、定时任务和算法调用属于内部实现，不应逐项包装成供其他团队调用的 HTTP 接口。

## 2. 当前已实现的本项目前后端接口（内部）

首版提供了下表 9 个方法与路径组合，其中 1 个为运行监控使用的健康检查。开发版 V0.2 在此基础上增加了配置快照与恢复、手动预览与提交、自动策划周度统计、结果周期统计和标签维护接口。这些路径都不是给客户账号、选题或内容生产系统调用的业务对接接口。

| 方法与路径 | 当前能力 | 与原型的主要差距 |
| --- | --- | --- |
| `GET /api/health` | 服务与数据库状态 | 用于运行状态检查 |
| `GET /api/config` | 读取当前配置 | 缺少完整阶段条件、回退规则 |
| `PUT /api/config` | 保存配置并递增版本号 | 只覆盖当前记录，未保存历史快照 |
| `GET /api/accounts` | 查询可用账号目录 | 缺少服务端业务筛选、分页、认证与粉丝等字段 |
| `GET /api/topics` | 查询可用选题目录 | 缺少标题筛选、大纲、标签、审核与有效期信息 |
| `GET /api/batches` | 查询自动或手动批次 | 批次列表不能直接替代周度汇总 |
| `GET /api/batches/{batch_id}` | 批次与条目详情 | 缺少账号级失败原因、内容版本与生产状态 |
| `GET /api/items` | 按账号名称或 ID 查询条目，并返回资料、生产/发布状态和替换权限 | 周期和其他业务筛选仍在页面侧完成 |
| `POST /api/batches/manual` | 创建手动待生成批次 | 尚未接入生产任务、异步回传、多选题分配、草稿 |

当前演示数据不代表真实 AI 运行记录。现有 `content_count` 和单一 `status` 字段不足以表达完整生产流程，后续应明确区分已规划、内容就绪、生成完成与已发布。

V0.2 之后已新增本项目页面可调用的 `GET /api/config/versions`、`POST /api/config/versions/{version}/restore`、`POST /api/manual-plans/previews`、`POST /api/manual-plans/previews/{preview_id}/submit`、`GET /api/manual-plans/tasks`、`GET /api/auto-planning/cycles`、`GET /api/auto-planning/cycles/{cycle_id}/failures`、`GET /api/planning-cycles`、`GET /api/planning-cycles/{cycle_id}/items`、`POST /api/items/{item_id}/replace-topic`、`GET /api/items/{item_id}/adjustments` 和 `GET/PUT /api/tag-taxonomy`。手动预览保存确定的账号选题分配，正式提交会创建任务记录；重复提交同一预览返回原批次。

## 3. 必须预留的六类跨系统业务接口（对外）

本节才是需要与其他团队确认的接口。以下入站路径按“客户推送到本系统”的方式举例，由本项目提供并让对方调用；出站路径由客户系统提供，供本项目调用。不能仅在本系统新增同名路由就视为完成对接。

| 对接能力 | 数据方向 | 建议接口或契约 | 主要用途 |
| --- | --- | --- | --- |
| 账号同步 | 客户账号系统 → 策划系统 | 本项目提供 `POST /api/integrations/accounts/sync` | 接收事实，更新本地账号档案 |
| 选题及营销内容同步 | 客户选题库 → 策划系统 | 本项目提供 `POST /api/integrations/topics/sync` | 接收选题、审核状态、有效期，更新本地目录 |
| 历史运营数据同步 | 客户运营系统 → 策划系统 | 本项目提供 `POST /api/integrations/content-history/sync` | 接收历史数据，供本地计算使用 |
| 策划及生产事件输出 | 策划系统 → 客户内容生产系统 | 客户提供事件接收地址，例如 `POST /integrations/planning-events` | 输出周期槽位包、真实内容就绪及版本变化 |
| 内容生产状态回传 | 客户内容生产系统 → 策划系统 | 本项目提供 `POST /api/integrations/content-status` | 接收生成结果，更新本地状态和使用计数 |
| 选题标签同步 | 策划系统 → 客户选题库 | 客户提供标签接收地址，例如 `POST /integrations/topic-tags` | 输出 T1–T5 固定标签配置与 T6 模型识别结果 |

### 3.1 三类输入至少需要哪些字段

**账号：** `account_id`、账号名称、平台、机构/分支行、属地、营销资格、人设、目标客群、兴趣、家庭身份、表达风格、认证状态、粉丝量、启停状态、`updated_at`。其中认证状态、粉丝量是手动策划原型明确要求的筛选基础；流量趋势由历史运营数据计算，需确定计算窗口。

**选题：** `topic_id`、标题、摘要/大纲、来源、内容类型、适用属地、是否营销、关联产品/活动、`generated_at`、`approval_status`、`approved_at`、`valid_from`、`valid_to`、状态、`updated_at`。热点来源和时效属性需在 PRD 中进一步定义，可先作为选题扩展字段接入。

**历史运营数据：** `content_id`、`account_id`、`topic_id`、标题、发布时间、内容类型、T2 经营作用、曝光、点赞、评论、收藏、互动数、状态、`updated_at`。历史 T2 字段的来源和缺失补标方式需要对齐；新选题的标签和匹配结果由策划系统维护。

三类同步共同保留：来源系统、同步批次号、全量/增量标志、记录唯一 ID、更新时间或来源版本、启停/删除标记。按唯一 ID 更新；同批重传可安全重试；旧版本不能覆盖新版本；返回接收数、成功数和逐条失败原因。全量分页未结束或单批未携带某条记录，不能据此推断该记录已删除。

原型要求首次全量、日常增量，策划任务读取本地已同步数据。可配套 `GET /api/integrations/sync-jobs/{job_id}` 查询耗时较长的同步任务。

### 3.2 一套输出协议容纳四种事件

| `event_type` | 输出内容 | 内容生产行为 |
| --- | --- | --- |
| `SLOT_PLAN_CREATED` | 周期、账号、槽位、投放日期、槽位类型和状态 | 记录规划；占位槽不生成内容 |
| `CONTENT_READY` | 槽位版本、真实选题、Fit、T1–T7、Agent 类型、完整 Content Agent Input | 提交对应内容的生产任务 |
| `SLOT_STATUS_CHANGED` | 新旧状态、原因、来源批次、发生时间 | 单纯状态变化不生成内容；绑定真实内容后通过同一任务键提交 |
| `CONTENT_VERSION_CHANGED` | 新旧版本、新旧选题、操作人、原因 | 按新版本更新或重新提交生产任务 |

事件共同保留 `event_id`、`schema_version`、`planning_cycle_id`、`planning_batch_id`、`account_id`、`slot_id`、`version`、`occurred_at`。生产事件追加 `topic_id`、`agent_type`、`content_agent_input`；可保留 `extension_context` 承载未来扩展。

`CONTENT_READY` 表示可以交给内容 Agent 生产，尚不代表生成完成。占位槽没有真实选题时不发送生产任务，`Fit=null`，内部占位计算值不发给内容生产系统。按 `event_id` 去重事件，同时按 `slot_id + version` 去重生产任务，防止不同事件造成重复生产。发送失败保留记录并重试。

### 3.3 回传和标签同步的特殊规则

- 生产回传至少携带 `event_id`、`production_task_id`、`slot_id`、`version`、生产状态和发生时间；生成成功时携带 `content_id`，失败时携带失败原因；成功时可附内容详情地址。
- 选题使用次数以“内容生成完成”为依据；重复成功回传不能重复计数。生成失败、仅完成策划、仅接收生产任务都不能计入。
- 替换产生新版本后，旧版本的迟到回传可归档，但不能覆盖当前内容状态。重新生成是否构成新的选题使用次数，需要 PRD 明确。
- “已发布”是禁止替换的判断依据。发布及审核状态可扩展到同一个回传协议，也可由历史内容同步提供；需明确唯一事实来源、状态时序及更新延迟。发布与替换的并发冲突还需客户生产系统配合校验版本或锁定状态。
- 标签同步需区分“标签字典版本”和“某个选题的标签关联”。T1–T5 由运营配置，T6 由模型识别；携带 `taxonomy_version`、标签稳定 ID、`topic_id`、关联版本及新增/移除标记，支持接收确认和重试。

## 4. 四个 Tab 的本项目前后端接口（内部）

以下 URL 只由本项目页面调用本项目后端，实现页面查询和操作。其他团队不需要按这些 URL 开发接口；若页面需要外部事实，由第 3 节的跨系统同步先进入本地数据，再由本节接口读取。

### 4.1 策划配置

| 状态 | 方法与路径 | 所需能力 |
| --- | --- | --- |
| 扩展 | `GET /api/config`、`PUT /api/config` | 账号规则、阶段条件、滚动窗口、目标比例、回退规则整体读取和保存 |
| 已实现基础版 | `GET /api/config/versions` | 列出最近的完整快照、操作人、时间、摘要 |
| 新增 | `GET /api/config/versions/{version}` | 查看完整历史快照 |
| 已实现 | `POST /api/config/versions/{version}/restore` | 恢复指定配置并生成新版本 |
| 新增 | `GET /api/config/audit-logs` | 配置操作日志 |
| 已实现基础版 | `GET /api/tag-taxonomy`、`PUT /api/tag-taxonomy` | T1–T5 标签字典读取、增删、版本化保存；T6 只读展示 |

配置保存需携带预期版本，防止多人编辑覆盖；账号规则与整套经营策略保存为同一快照。标签字典可独立版本化，并由每次策划记录引用所用版本。阶段条件采用受限的字段、运算符、阈值模型，不接收可执行表达式。

### 4.2 AI 自动策划

| 状态 | 方法与路径 | 所需能力 |
| --- | --- | --- |
| 新增 | `GET /api/auto-planning/overview?cycle_start=...` | 周度参与、成功、失败账号数，运行状态和更新时间 |
| 已实现基础版 | `GET /api/auto-planning/cycles` | 根据已存批次与条目汇总历史周度运行结果 |
| 已实现基础版 | `GET /api/auto-planning/cycles/{cycle_id}/failures` | 展示已有失败条目；只有批次失败时显示批次原因 |
| 复用并扩展 | `GET /api/batches/{batch_id}` | 需要时查看关联批次信息 |

运营原型只要求查看结果与刷新。定时主批次、新账号增量、营销审核状态变化、热点补齐等触发点由后台调度或内部服务承担。先预留内部调用能力；是否需要运维 HTTP 触发/重试接口，按部署方案决定，不直接添加运营“立即运行”入口。

同一周可能有多个主批次/增量批次，周度账号数和状态需由后端按业务规则聚合，不能把批次计数直接相加。算法参数、Fit 分数和计算过程不放入运营页面响应。

### 4.3 手动策划

| 状态 | 方法与路径 | 所需能力 |
| --- | --- | --- |
| 扩展 | `GET /api/accounts` | 按投放日期、认证状态、粉丝量、流量趋势筛选；返回总数及分页 |
| 新增 | `POST /api/manual-plans/account-selections` | 按筛选条件随机抽取指定数量账号，返回选取结果和 `selection_id` |
| 扩展 | `GET /api/topics` | 按标题、内容类型查询当前可用选题，返回大纲与分页 |
| 已实现 | `POST /api/manual-plans/previews` | 输入日期、指定或随机抽取的账号与多个选题，输出确定的分配明细和 `preview_id` |
| 新增 | `POST /api/manual-plans/drafts` | 保存草稿，不提交内容生产 |
| 新增 | `GET /api/manual-plans/drafts`、`GET /api/manual-plans/drafts/{draft_id}`、`PUT /api/manual-plans/drafts/{draft_id}` | 列出、恢复、更新草稿 |
| 已实现基础版 | `POST /api/manual-plans/previews/{preview_id}/submit` | 按已确认的分配生成批次，重复提交返回同一批次 |
| 已实现原接口 | `POST /api/batches/manual` | 兼容直接输入账号和选题创建本地批次 |
| 新增 | `GET /api/jobs/{job_id}` | 查询分配、任务投递及生成进度，显示逐项失败原因 |

业务规则：仅追加；账号不足时阻止提交；一个选题时全部账号共用，多个选题时每个账号随机分配一个，不要求平均。服务端保存预览分配，提交时校验有效性，避免提交时重新抽签造成预览与结果不一致。账号名、选题标题和资格均从服务端可信目录解析。

异步请求已接收时显示待生成/生成中；收到生成完成回传后才进入相应后续状态。“生成后直接待审核”需与内容生产系统的审核流程对齐。当前页面的城市、人设筛选是演示实现，尚未覆盖原型指定的四个运营筛选维度。

### 4.4 策划结果

| 状态 | 方法与路径 | 所需能力 |

## 5. 后端内部能力与技术依赖边界

除第 3 节六类业务对接外，统一身份认证和第三方模型调用可能涉及其他团队或供应商，但它们属于技术依赖；需要单独确认，不应混入账号/选题/生产的数据契约。数据库、调度器、策划算法和后台任务则由本项目内部负责。

- **用户身份与权限：** 预留客户统一认证适配和当前用户/权限查询，例如 `GET /api/me`。配置保存、回滚、提交、替换的操作人取自认证身份；登录方式依客户 SSO 方案确定。
- **服务间认证：** 同步、回调与事件投递分别认证，按客户网关方案使用凭证或签名；模型密钥和数据库凭证仅在服务端使用。
- **列表与错误：** 新接口采用明确的分页、排序、筛选和业务错误码；建议保留 `request_id`。现有数组响应若改为分页对象，需要前后端一起适配。
- **异步与幂等：** 长任务返回任务 ID；提交接口保留幂等键；生产状态、批次状态、槽位状态分别建模。已接收任务不等于生成成功。
- **ID 与版本：** 区分客户业务 ID、本地自增主键、周期 ID、批次 ID、稳定槽位 ID、内容版本和生产任务 ID。现有条目 ID 可继续供页面使用，需明确它与稳定槽位 ID 的映射。
- **时间与统计：** 接口时间戳带时区，周周期按约定业务时区计算；投放日期与实际发布时间分开。选题使用次数与去重选题数使用各自口径。
- **内部 AI 适配：** 标签识别任务、[普通选题画像与向量准备接口](TOPIC_PROFILE_VECTOR.md)、[批次账号画像与向量准备接口](ACCOUNT_PROFILE_VECTOR.md)属于本项目内部运转，提供画像版本、向量结果回写和 AI 候选查询，不是客户账号或选题库接口。可配置的标签、选题向量和账号向量进程已接入项目模型服务契约；仍需提供具体模型服务，接入正式匹配与 Content Agent 路由。若调用第三方模型 API，它是本项目依赖的技术服务，需另行确认模型供应方、鉴权和调用约束；它不等同于客户账号、选题、历史数据及内容生产系统之间的六类业务对接。内容 Agent 属于哪个系统按后续 PRD/部署方案确定。

## 6. 实施顺序与待确认事项

建议先打通账号/选题同步 → 手动预览与提交 → 内容就绪事件 → 生成状态回传 → 结果查询，形成第一条真实业务闭环；同阶段把稳定槽位 ID、版本和幂等设计落实。

随后补齐四页原型剩余能力：配置快照/回滚、标签维护及同步、历史运营数据、后台自动调度、周度汇总与失败明细、选题替换及版本记录。历史运营数据是自动策划前置条件；快照版本应在自动任务接入前可用。导出、实时推送、运维重放界面可按实际需要后置，可靠投递和重试能力应随首次对接实现。

目前五张业务表不足以保存全部接口数据。后续需要扩展账号/选题字段，并承载配置历史、标签及关联、运营历史、账号级运行结果、草稿/预览、槽位版本/调整记录、同步任务/事件投递记录。具体拆表随 PRD 决定，遵守 `godp_` 前缀、自增 ID、审计字段、无外键等现有数据库规范。

PRD 或对接会议需要明确：

1. 三类输入的提供方、唯一 ID、全量范围、增量频率、推送/拉取方式和鉴权。
2. 内容 Agent 由哪个系统运行，输入模板、任务接收确认、回调方式和超时处理。
3. 审核/发布状态的事实来源；替换与发布的并发处理；重新生成的计数口径。
4. 周起止、定时执行时间、增量触发条件、失败重试范围、热点输入来源。
5. 生命周期条件与回退规则、流量趋势窗口、选题去重及标签语义规则。
6. 手动条目是否可替换，草稿可见范围，以及最终用户/机构权限范围。

以上事项可在后续 PRD 中确认，不影响现在先确定数据契约、模块边界和模拟对接样例。
